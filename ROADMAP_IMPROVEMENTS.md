### SEC-004: Отсутствие rate limiting на ingestion endpoint
**Файл:** `src/server/WindowsInventoryLiteServer.cs` — обработчики `/api/v1/inventory` и `/api/v1/linux/inventory`
**Проблема:** Атакующий может DoS-ить сервер, флудя отчётами (CPU, диск). Нет защиты от перебора токенов.
**Решение:**
- [ ] Token bucket / sliding window per IP + per token
- [ ] Лимиты: например, 60 req/min per token, 200 req/min per IP
- [ ] Возврат `429 Too Many Requests` с `Retry-After`

**Оценка:** 2-3 дня
**✅ Подтверждено 2026-08-24:** grep по кодовой базе не находит никакого rate-limiting механизма. Реальный, не закрытый пробел.

---

### SEC-009: Отсутствие подписи/верификации отчётов клиента
**Проблема:** Любой владелец токена может подделать данные инвентаризации. Нет гарантии авторства и целостности.  
**Решение:**
- [ ] Ed25519 подпись отчёта клиентским приватным ключом
- [ ] Сервер хранит публичные ключи клиентов (при регистрации — TOFU или CA)
- [ ] Формат: `payload || signature` или JWS (detached)
- [ ] Опционально: mTLS для клиентов (cert-based auth)

**Оценка:** 5-7 дней (крупная фича)  
**Примечание:** Можно отложить до P1, если threat model не требует non-repudiation
**✅ Подтверждено 2026-08-24:** подписи/верификации подлинности отчёта действительно нет - только ingestion-токен как единственный барьер. Реальный, осознанно не закрытый пробел (крупная фича, требует отдельного дизайна - раздачи/хранения ключей клиентов, TOFU-модели и т.д.). Не блокер, но валиден как задача на будущее.

### SEC-010: HSTS-заголовок отсутствует (формулировка "нет HTTPS enforcement" - неверна)
**Решение (сузить до реального пробела):**
- [ ] Добавить `Strict-Transport-Security` заголовок на ответах, когда `UseHttps` включён

**Оценка:** 0.5 дня
**⚠️ Частично подтверждено, формулировка скорректирована 2026-08-24:** исходная версия пункта была неверна - HTTPS уже полностью поддерживается и настраивается (импорт сертификата, `Settings > Certificate`, история сертификатов, обязательный редирект не нужен - HTTP просто можно не включать). Единственное, чего не нашёл grep'ом - явного заголовка `Strict-Transport-Security`. Это узкий, отдельный пункт, а не "нет HTTPS enforcement" целиком.

## 🟠 P1 — HIGH: АРХИТЕКТУРА

### ARCH-001: Монофункциональный сервер в одном файле
**Файл:** `src/server/WindowsInventoryLiteServer.cs` — **фактически 10983 строки** (не "2000+", как в исходной версии пункта), 1 класс.
**Проблема:** Нарушение SRP: HTTP routing, auth, storage, AD lookup, scheduling, UI serving — всё в одном.
**Решение (скорректировано под реальный стек - .NET Framework 3.5, без DI-контейнеров в проекте):**
- [ ] Разбить на модули по мере роста, без обязательного DI-контейнера (исходное предложение `Microsoft.Extensions.DependencyInjection` не подходит - проект осознанно минималистичен, без внешних DI-фреймворков)

**Оценка:** переоценить при реальном планировании, не 5-7 дней
**⚠️ Частично подтверждено, формулировка скорректирована 2026-08-24:** сам факт "всё в одном файле" - правда, но это уже известный, осознанный компромисс проекта (см. `docs/backlog.md`/память проекта: "не текущая проблема, но стоит пересмотреть, если файл продолжит расти"), не новая находка. Конкретное предложение (DI-контейнер, интерфейсы под моки) противоречит принятому в проекте минимализму - не годится как есть.

### ARCH-002: JSON-файлы как "БД" — нет ACID, индексов (утверждение "нет file locking" - неверно)
**Файлы:** `WindowsInventoryLiteServer.cs`
**Проблема (скорректировано):**
- Полное чтение всех файлов в память при каждом запросе списка клиентов
- Нет индексов
- ~~Race condition при параллельной записи (нет file locking)~~ - **неверно**, см. ниже
**✅/❌ Частично подтверждено 2026-08-24:** в коде уже есть минимум 8 выделенных `lock`-объектов (`installJobsLock`, `reportFileLock`, `configFileLock`, `licensesLock`, `certificateHistoryLock` и др.), явно защищающих именно эти файловые операции - утверждение "нет file locking" ложно. Отсутствие ACID/индексов в плоских JSON-файлах - архитектурно верное наблюдение, но это осознанный выбор для лёгкого инструмента, а не однозначный баг.
